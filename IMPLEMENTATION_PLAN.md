# План реализации (итерации)

Опирается на [REQUIREMENTS.md](REQUIREMENTS.md). Каждая итерация маленькая, с чётким критерием «готово/не готово», и делает предположения из раздела 5 требований проверенными фактами как можно раньше — чтобы не строить весь пайплайн на непроверенных допущениях.

## Итерация 0 — Базовое подключение
- [x] Готово (2026-09-06)

**Сделать:** Установить Gadgetbridge, запейрить Band 9 (вместо/наряду с Mi Fitness).
**Проверка:** Gadgetbridge показывает живые базовые данные с часов (батарея, шаги) — значит связь установлена и стабильна.

## Итерация 1 — Пульс в тренировке вообще пишется
- [ ] Готово

**Сделать:** Короткая тестовая тренировка (5 мин, режим плавания/открытой воды), без воды — просто проверка механики. Синхронизировать, экспортировать БД (Export DB → CSV).
**Проверка:** В CSV есть строки с ЧСС и таймстампами, покрывающие временное окно тренировки. Если данных нет — это блокер, дальше не идём, разбираемся отдельно (другой режим тренировки / ручной запуск realtime HR в Gadgetbridge).

## Итерация 2 — Частота сэмплов достаточна
- [ ] Готово

**Сделать:** На данных из итерации 1 посчитать среднее и максимальное расстояние между соседними таймстампами ЧСС.
**Проверка:** Интервал ≤ ~10 сек (см. допущение в REQUIREMENTS.md §5). Если сильно реже (например, раз в минуту) — пайплайн в текущем виде не годится для анализа задержек дыхания по 1-4 минуты, нужно искать другой способ поднять частоту (другой режим тренировки, настройки Gadgetbridge) до перехода к следующей итерации.

## Итерация 3 — Поведение датчика в реальных условиях (вода + апноэ)
- [ ] Готово

**Сделать:** Реальный короткий тест в бассейне: 2-3 короткие задержки дыхания (по 30-60 сек, с напарником по безопасности), часы в режиме тренировки, без меток пока — просто смотрим сырые данные.
**Проверка:** После экспорта визуально видно на графике правдоподобное поведение (падение ЧСС во время удержания) без больших провалов/выпадений данных именно в моменты задержки. Задокументировать любые артефакты — это и есть проверка допущения про PPG при апноэ из REQUIREMENTS.md §5.

## Итерация 4 — Механизм меток
- [ ] Готово

**Сделать:** Выбрать и настроить простейший способ ставить one-tap метку с таймстампом на телефоне (готовое приложение-секундомер/лог событий, либо минимальный кастомный вариант, если готового не найдётся).
**Проверка:** Несколько тестовых нажатий подряд с известными интервалами (например, по секундомеру) → экспортированные из механизма меток таймстампы совпадают с реальными интервалами с точностью до пары секунд.

## Итерация 5 — Сквозной прогон (dry run)
- [ ] Готово

**Сделать:** Полная тренировочная сессия по-настоящему: старт тренировки на часах → 2-3 задержки дыхания с метками старт/стоп на телефоне для каждой → синхронизация → экспорт.
**Проверка:** Метки по времени попадают ровно на видимые характерные участки графика ЧСС (падения/восстановления) при ручном сопоставлении вручную в таблице/на глаз.

## Итерация 6 — Скрипт анализа, версия 1
- [ ] Готово

**Сделать:** Python-скрипт, который берёт CSV с ЧСС и CSV/файл с метками из итерации 5 и для каждой попытки считает: ЧСС до начала, минимальную ЧСС, % падения, время восстановления; строит график всей сессии с отметками попыток.
**Проверка:** Запуск на данных итерации 5 даёт числа, совпадающие с тем, что видно на глаз на графике (в пределах разумной погрешности).

## Итерация 7 — Устойчивость скрипта
- [ ] Готово

**Сделать:** Прогнать скрипт на второй/третьей реальной сессии (другой день, другое количество попыток, возможно другие паттерны — например, пропущенные сэмплы, попытки впритык друг к другу).
**Проверка:** Скрипт не падает и даёт корректные по смыслу результаты на разных сессиях без правок кода под каждый конкретный случай.

## Итерация 8 — Оформление процесса
- [ ] Готово

**Сделать:** Короткий `RUNBOOK.md` — пошаговая шпаргалка «что делать перед тренировкой / во время / после», без технических деталей реализации.
**Проверка:** Определение готовности (DoD) из REQUIREMENTS.md §7 выполняется целиком, руководствуясь только RUNBOOK.md, без сверки с этим планом или требованиями.

**Принцип порядка:** итерации 0-3 — валидация допущений из REQUIREMENTS.md §5 на реальном устройстве, до того как писать какой-либо код анализа. Если итерация 1, 2 или 3 показывает, что допущение не подтвердилось — план останавливается на этом шаге и пересматривается, а не продолжается «в надежде, что дальше само наладится».
