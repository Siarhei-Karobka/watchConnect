# План реализации (итерации)

Опирается на [REQUIREMENTS.md](REQUIREMENTS.md). Каждая итерация маленькая, с чётким критерием «готово/не готово», и делает предположения из раздела 5 требований проверенными фактами как можно раньше — чтобы не строить весь пайплайн на непроверенных допущениях.

- [x] Готово (2026-09-06)

**Проверка:** Gadgetbridge показывает живые базовые данные с часов (батарея, шаги) — значит связь установлена и стабильна.

## Итерация 1 — Пульс в тренировке вообще пишется
- [x] Готово (2026-09-07)

**Сделать:** Короткая тестовая тренировка, без воды — просто проверка механики. Синхронизировать, экспортировать.
**Проверка:** Есть строки с ЧСС и таймстампами, покрывающие временное окно тренировки.

**Результат (см. LOG.md «Итерация 1 и 2 — РЕШЕНО»):** рабочий рецепт — режим тренировки **«Киберспорт»** (в самом Gadgetbridge может отображаться как «Эспорт» — особенность локализации; внутренний код Xiaomi-протокола `SPORTS_FREESTYLE`, не требует движения, не ставится на паузу при неподвижности — решает и вопрос авто-паузы из-за неподвижности при апноэ) + экспорт через кнопку **«поделиться» (⤴) на экране самой активности** в приложении Gadgetbridge → .fit-файл с посэмпльными `record`-сообщениями. Важно: **Export DB** (полная SQLite-база) и **«Инструменты разработчика → подробная информация»** для этой же тренировки дают только сводку (avg/min/max) — этими двумя путями посэмпльные данные не достать, несмотря на то что они кажутся более «полными» экспортами.

## Итерация 2 — Частота сэмплов достаточна
- [x] Готово (2026-09-07)

**Сделать:** На данных из итерации 1 посчитать среднее и максимальное расстояние между соседними таймстампами ЧСС.
**Проверка:** Интервал ≤ ~10 сек (см. допущение в REQUIREMENTS.md §5).

**Результат:** интервал между соседними ЧСС-сэмплами — ровно 1.0 сек, стабильно на всей ~15-минутной тестовой сессии (после ~14 сек на захват сигнала датчиком в начале). Существенно лучше требуемого порога.

## Итерация 3 — Поведение датчика в реальных условиях (вода + апноэ)
- [~] Объединена с итерацией 5 (2026-09-07) — отдельный «пустой» заплыв без меток пропускаем, проверка сырых данных при апноэ и работы режима «Киберспорт» в воде делается в рамках первого настоящего заплыва с метками (итерация 5), не отдельным шагом.

**Что именно проверить (перенесено в итерацию 5):** после первого реального заплыва — визуально видно на графике правдоподобное поведение (падение ЧСС во время удержания) без больших провалов/выпадений данных именно в моменты задержки. Задокументировать любые артефакты — это и есть проверка допущения про PPG при апноэ из REQUIREMENTS.md §5. Заодно первая проверка режима «Киберспорт» непосредственно в воде (см. открытый вопрос в REQUIREMENTS.md §5). Если тут что-то пойдёт не так — заплыв придётся повторить уже после разбора проблемы, прежде чем считать итерацию 5 пройденной.

## Итерация 4 — Механизм меток
- [ ] Готово

**Сделать:** Собственная веб-страница (PWA-подобная) с двумя большими кнопками СТАРТ/СТОП вместо готовых инструментов автоматизации (MacroDroid/Termux/сторонние секундомеры — рассмотрены и отклонены в пользу простого в обновлении своего решения). Метки хранятся только в `localStorage` браузера на телефоне (без внешних сервисов, см. REQUIREMENTS.md §4); экспорт — копированием CSV-текста прямо со страницы. Опубликована через GitHub Pages: https://siarhei-karobka.github.io/watchConnect/webapp/apnea_labels.html (репозиторий https://github.com/Siarhei-Karobka/watchConnect, публичный, под личным GitHub-аккаунтом — без логина на телефоне; исходник — `webapp/apnea_labels.html`, обновления выкатываются `git push` в ветку `master`, без переустановки на телефоне). На телефоне открыть ссылку в Chrome → «Добавить на главный экран».
**Проверка:** Несколько тестовых нажатий подряд с известными интервалами (например, по секундомеру) → скопированные из страницы CSV-таймстампы совпадают с реальными интервалами с точностью до пары секунд.
**Известное ограничение:** без офлайн-кэша (service worker) страница должна быть уже открыта во вкладке до потери сети у бассейна — если вкладку закрыть без интернета, заново открыть не получится до восстановления связи. Не блокирует итерацию; пересмотреть, если окажется проблемой на практике.

## Итерация 5 — Сквозной прогон (dry run) + проверка датчика при апноэ (бывшая итерация 3)
- [ ] Готово

**Сделать:** Полная тренировочная сессия по-настоящему, один запуск тренировки на часах в режиме «Киберспорт» на всю сессию: → 2-3 задержки дыхания с метками старт/стоп на телефоне для каждой → синхронизация → экспорт через «поделиться» → .fit.
**Проверка (две сразу):**
1. Метки по времени попадают ровно на видимые характерные участки графика ЧСС (падения/восстановления) при ручном сопоставлении вручную в таблице/на глаз.
2. Поведение ЧСС во время задержек правдоподобно (падение без больших провалов/выпадений данных именно в эти моменты) — бывшая проверка итерации 3 из REQUIREMENTS.md §5. Заодно первая проверка режима «Киберспорт» непосредственно в воде.

Если проверка 2 не проходит — это блокер, требующий отдельного разбора (не переходить к итерации 6, пока не решится).

## Итерация 9 (опционально, по желанию) — Полировка
Кандидаты, только если появится реальная потребность после итерации 8: один общий скрипт/команда для экспорта+анализа за раз; сохранение истории сессий для сравнения прогресса тренировок во времени.

Также рассмотрено при обсуждении итерации 4, но осознанно отложено (см. REQUIREMENTS.md §5): Gadgetbridge ≥0.92.0 умеет автоматически экспортировать по-сэмпльный .fit при каждой синхронизации (Settings → Automations → Auto export FIT tracks, заявленно поддерживает Xiaomi protobuf/Band 9) — если ручной экспорт станет утомительным, сначала сверить его по-сэмпльность с уже проверенным ручным экспортом через `fitparse`, прежде чем полагаться на него в реальной сессии. У Gadgetbridge также есть Intent API (broadcast-интенты для триггера синхронизации/экспорта) — теоретически наша веб-страница меток не сможет его вызвать напрямую (браузер не шлёт Android-intent), но кастомное мини-приложение (не веб) или MacroDroid могли бы. Перенос файлов на компьютер сейчас ручной (осознанный выбор) — Syncthing (с отключённым глобальным discovery/relay ради соответствия §4) остаётся кандидатом, если это станет узким местом.
