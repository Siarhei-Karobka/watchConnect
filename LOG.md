## 2026-09-07 — Итерация 1 — Пульс в тренировке (ЗАБЛОКИРОВАНО)

Что делали:
- Тестовая тренировка 5 мин на часах в режиме «велоспорт в помещении» (без плавания — см. отдельную заметку про авто-паузу в REQUIREMENTS.md §5).
- Синхронизировали, экспортировали активность двумя способами: (1) «поделиться»/экспорт одной активности → .fit-файл; (2) Database Management → Export DB → полная SQLite-база.
- .fit-файл разобрали через `fitparse`: там только `lap`/`session` с агрегатами (avg/min/max ЧСС за всю тренировку), ни одной записи `record` с посэмпльными данными.
- SQLite-базу разобрали вручную (`sqlite3`): `BASE_ACTIVITY_SUMMARY` содержит только маленький бинарный блок (175 байт — явно агрегат, не массив сэмплов), `SUMMARY_DATA`/`GPX_TRACK`/`RAW_DETAILS_PATH` пустые. Фоновая таблица `XIAOMI_ACTIVITY_SAMPLE` (ежеминутные данные) на весь период тренировки показывает HEART_RATE=0 — то есть на время тренировки фоновая запись, по всей видимости, отключается, а данные тренировки с повышенной частотой в доступные через SQL таблицы не попадают. Есть только запись в `XIAOMI_ACTIVITY_FILE`, указывающая на сырой protobuf-файл в приватном хранилище Gadgetbridge на телефоне — но он не распарсен в БД.
- Проверили через веб-поиск/codeberg issue #4608 (тот же источник, что уже был в REQUIREMENTS.md §2): разработчики Gadgetbridge подтверждают, что для Xiaomi Smart Band 9 подробные посэмпльные ЧСС-данные по тренировке сейчас парсятся не полностью — известное ограничение, а не баг конкретно велотренажёра/индор-сайклинга.

Результат:
- В экспортированных данных (ни .fit, ни SQLite) нет построчных ЧСС-сэмплов с таймстампами внутри окна тренировки — только сводные avg/min/max за всю сессию.
- Итерация 1 в изначальном виде («в CSV есть строки с ЧСС и таймстампами, покрывающие окно тренировки») не пройдена.

Вывод / что дальше:
- Это подтверждённый (не гипотетический) блокер верхнего уровня допущения из REQUIREMENTS.md §5 про доступность посэмпльных данных через Gadgetbridge.
- Направления для проверки, прежде чем пересматривать весь подход:
  1. Попробовать режим плавания/открытой воды — в обсуждениях Gadgetbridge упоминается, что для части видов активности парсинг детальнее (могло не совпадать с индор-сайклингом). Заодно это разрешит вопрос из предыдущей заметки про авто-паузу на неподвижности.
  2. Проверить в самом приложении Gadgetbridge (не через экспорт), показывает ли график ЧСС этой тренировки детализацию по времени — если да, данные где-то есть, просто не там, где искали.
  3. Посмотреть nightly/dev-сборку Gadgetbridge — в CHANGELOG есть записи вида «Xiaomi-protobuf: Improve workout parsing», то есть поддержка активно дорабатывается и может отличаться от текущей установленной версии.
  4. Если ничего не поможет — вернуться к рассмотрению отклонённой альтернативы «Notify for Xiaomi & Mi Fitness» (платное приложение) как запасного варианта, раз open-source путь пока не даёт нужных данных.
- **Доп. проверка (2026-09-07):** график ЧСС этой тренировки пуст и в самом приложении Gadgetbridge (не только при экспорте) — при этом min/avg/max отображаются. Значит, проблема не в способе экспорта/чтения базы, а в том, что для режима «индор-сайклинг» на Band 9 Gadgetbridge в принципе не парсит/не хранит посэмпльные данные, только агрегаты. Сужает следующий шаг: нужно проверить, отличается ли это для другого типа тренировки (плавание/открытая вода), а не искать данные другим способом в этом же экспорте.

## 2026-09-07 — Итерация 1 и 2 — Пульс пишется, частота отличная (РЕШЕНО)

Что делали:
- После блокера с велотренировкой (см. запись выше) искали режим тренировки без требования движения — подошёл **«Киберспорт»** (внутреннее имя Xiaomi-протокола `SPORTS_FREESTYLE`, subtype=8; в самом экране активности Gadgetbridge подписывает его как «Эспорт» — похоже, косяк локализации, а не отдельный режим): по смыслу рассчитан на неподвижность, как и апноэ.
- Тест: ~15 минут неподвижно на месте в режиме «Киберспорт», синхронизация.
- Проверили график ЧСС прямо в приложении Gadgetbridge (не через экспорт) — впервые увидели реальную кривую по времени, а не пустой график.
- Экспорт БД (Export DB → SQLite) и «Инструменты разработчика → подробная информация» (JSON+bin) для этой сессии — оба варианта снова дали только сводку (avg/min/max), без посэмпльных данных. Проверили расширенный список таблиц (`GENERIC_HEART_RATE_SAMPLE` и другие) — везде 0 строк для этой сессии.
- Нашли третий путь экспорта: кнопка «поделиться» (⤴) на экране самой активности → .fit-файл. В этот раз .fit получился 5898 байт (у велотренировки был 400 байт) — и это оказался правильный путь.

Результат:
- В .fit-файле — 916 записей `record`, по одной на каждую секунду сессии (916 сек = ~15.3 мин). Из них 902 содержат `heart_rate`.
- Интервал между соседними ЧСС-таймстампами = ровно 1.0 сек везде (min=max=avg=1.0), без пропусков после первых ~14 сек (видимо, время на захват сигнала датчиком в начале).
- Режим «Киберспорт» не прерывался и не ставился на паузу за все 15 минут неподвижности.

Вывод / что дальше:
- Итерация 1 пройдена: рабочий путь — режим тренировки «Киберспорт» (не плавание/открытая вода, не велотренажёр) + экспорт через кнопку «поделиться» на экране активности (не Export DB, не «Инструменты разработчика»).
- Итерация 2 фактически тоже пройдена на этих же данных: интервал 1.0 сек ≪ требуемых ≤10 сек — допущение из REQUIREMENTS.md §5 не просто подтвердилось, а превзошло ожидания (там предполагалось 1-5 сек).
- Открытый вопрос для итерации 3 (бассейн): работает ли режим «Киберспорт» физически в воде (водостойкость — свойство корпуса часов, а не режима, но именно в воде надо убедиться, что часы это не блокируют программно). Раз в реальной сессии не нужно трогать экран под водой (по REQUIREMENTS.md §4 — телефон и взаимодействие только на бортике), сам факт "не спортивный для плавания" режим не должен быть проблемой, но это не проверено на практике.
- Название режима на часах — «Киберспорт»; в списке активностей/на экране активности в Gadgetbridge встречается подпись «Эспорт» для этой же записи — не путать с отдельным режимом. Внутренний код `SPORTS_FREESTYLE` — ориентир для поиска в базе.

## 2026-09-06 — Итерация 0 — Базовое подключение

Что делали:
- Запейрили Band 9 с Mi Fitness (штатно).
- Ключ авторизации для Gadgetbridge достали non-rooted-phone методом: экспорт логов приложения (Mi Fitness → лог-архив), в них нашлось поле `encryptKey`/`token` в JSON-блоке `device.detail`. Ключ введён в Gadgetbridge в формате `0x<encryptKey>`.
- Первая попытка подключения не удалась ("authentication failed") — часы оставались привязаны к телефону на уровне системного Bluetooth Android, это мешало хендшейку Gadgetbridge. Забыли устройство в Настройки → Bluetooth Android, после чего Gadgetbridge вообще перестал видеть часы при сканировании.
- Починили: разбудили экран часов перед сканированием (иначе не отвечают на BLE-скан), запустили поиск в Gadgetbridge заново, на экране часов появился запрос на подтверждение сопряжения (галочка) — подтвердили на самих часах.

Результат:
- Часы подключены к Gadgetbridge, видны живые данные (батарея, шаги).

Вывод / что дальше:
- Работающий рецепт пейринга Xiaomi protobuf-устройства с Gadgetbridge: (1) штатный пейринг с Mi Fitness → (2) ключ из логов приложения → (3) НЕ трогать системные настройки Bluetooth Android, пейринг делает сам Gadgetbridge → (4) экран часов бодрствует во время скана → (5) подтвердить галочкой на самих часах.
- Ключ авторизации в этот лог намеренно не записан (секрет уровня пароля) — см. предупреждение в REQUIREMENTS.md.
- Переходим к итерации 1 — проверка, что во время тренировки пульс действительно пишется.
